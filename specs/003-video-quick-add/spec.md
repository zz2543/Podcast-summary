# Feature Specification: 视频一键送总结（Mac）

**Feature Branch**: `002-macos-native`（未单独开分支：本特性建立在尚未合并的 002 原生客户端之上）
**Created**: 2026-09-24
**Status**: Implemented（手动验收项见 plan.md）
**Input**: User description: "在打开 B 站 / YouTube 视频的时候（网页端和 app），通过某种快捷方式，一键加入到我们的 app 中做总结。" 本轮只做 Mac，入口为全局快捷键；手机端、系统分享菜单扩展、浏览器扩展不在本轮。（最初还有一个浏览器书签入口，已实现后按用户要求于 2026-09-24 删除，见 Clarifications。）

## 背景

「把一个 B 站 / YouTube 视频拿去总结」这件事，系统已经会做：提交后会抓取音频、识别分享文案里的链接、去掉跟踪参数、对重复链接给出"已存在"。
缺的是**入口**——今天必须切到 Podsum、打开提交面板、粘贴、确认，看视频时的一个念头要走四步。本特性把它压到一步，并且不把人从正在看的视频里拽走。

## Clarifications

### Session 2026-09-24

- 书签入口（`podsum://` 链接协议 + 浏览器书签）实现后被用户要求删除，只保留全局快捷键。原 User Story 1（书签）移除、其后的故事编号顺延，FR-001、FR-002 作废。
- Q: 关闭主窗口后 Podsum 是否继续运行？ → A: 继续运行，留在菜单栏，后端不停；⌘Q 或菜单栏"退出"才真正退出（取代 002 的"关窗即退出"）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 按一个全局快捷键，把当前视频送去总结 (Priority: P1)

用户在看视频时按下全局快捷键（默认 ⌥⌘S，可改）。如果最前面的是受支持的浏览器，Podsum 直接读取当前标签页的地址，无需复制；如果最前面是别的 app（例如 B 站 Mac 客户端），Podsum 读取剪贴板里的链接或分享文案——用户先点"复制链接"再按键即可。结果同样以系统通知反馈，焦点不离开当前 app。

**Why this priority**: 唯一的入口。真正的"一键"，并且覆盖 B 站 Mac 客户端这类没有地址栏的 app；前提是 Podsum 在运行（关窗后常驻菜单栏，见 FR-016），浏览器首次使用需要授权。

**Independent Test**: Podsum 运行中 → 在 Safari 打开一个 YouTube 视频 → 按 ⌥⌘S → 收到"已加入"通知；再在 B 站 Mac 客户端复制一个视频的分享链接 → 切到任意非浏览器 app → 按 ⌥⌘S → 收到"已加入"通知。

**Acceptance Scenarios**:

1. **Given** 最前面是 Safari / Chrome / Arc / Edge 且当前标签页是视频页，**When** 用户按快捷键，**Then** 提交当前标签页的视频，剪贴板内容被忽略，通知反馈结果。
2. **Given** 最前面不是受支持的浏览器，剪贴板里是 `【标题】https://b23.tv/xxxx` 这样的分享文案，**When** 用户按快捷键，**Then** 从中识别出链接并提交。
3. **Given** 某浏览器是第一次被读取，**When** 用户按快捷键，**Then** 系统弹出一次授权请求；用户允许后本次提交照常完成，之后不再询问。
4. **Given** 用户拒绝了对某浏览器的授权，**When** 在该浏览器里按快捷键，**Then** 退回读剪贴板；若剪贴板里也没有视频链接，通知说明"读不到当前页面地址"，并告诉用户去哪里补授权。
5. **Given** 最前面是受支持的浏览器，但当前标签页不是视频页，剪贴板里恰好有一个视频链接，**When** 用户按快捷键，**Then** 以当前标签页为准，提示"这不是可识别的视频链接"，不回退到剪贴板（避免提交用户没在看的东西）。
6. **Given** 用户在设置里把快捷键改成另一组合，**When** 按新组合，**Then** 生效；旧组合不再响应。若新组合已被别的程序占用，设置里当场提示"这个组合用不了"。

### User Story 2 - 看到快捷提交的去向 (Priority: P2)

用户连续送了几个视频，想知道哪些进去了、哪些失败了、哪些还在排队——即使通知被关掉了，或者当时没看到。

**Why this priority**: 通知是瞬时的；没有一个可回看的地方，失败会被悄悄吞掉。它是前两个故事的兜底，但前两个故事单独也能用。

**Independent Test**: 关闭 Podsum 的系统通知权限 → 用快捷键送一个视频、再在非视频页按一次 → 打开 Podsum，能在一处看到两条记录及各自结果。

**Acceptance Scenarios**:

1. **Given** 用户送出了若干链接，**When** 打开 Podsum，**Then** 能看到最近的快捷提交记录：链接/标题、来源入口（快捷键读浏览器或读剪贴板）、时间、结果（排队中 / 提交中 / 已加入 / 已存在 / 无法识别 / 失败及原因）。
2. **Given** 某条记录失败（例如视频需要登录、下载超时），**When** 用户在记录上选择重试，**Then** 该链接重新进入队列。
3. **Given** 某条记录已成功加入，**When** 用户点击它（或点击对应通知），**Then** 打开该集详情。

---

### Edge Cases

- **后端还没起来**（刚启动、正在重启）：链接留在队列里，就绪后按先来后到依次提交；期间通知显示"已收到，等 Podsum 准备好后提交"。
- **Podsum 尚未配置凭据，后端起不来**：链接保留在队列里不丢；通知明确说"Podsum 还没配置好，链接已保存"，配置完成后自动提交。
- **队列里还有链接时 Podsum 被退出**：下次启动后继续提交，不丢、不重复。
- **短时间内重复送同一个链接**（连按两次快捷键）：只提交一次，第二次反馈"已在队列中"。
- **同一个视频的不同写法**（地址栏带尾斜杠与 `spm_id_from`、分享带 `vd_source`、`youtu.be` 与 `watch?v=`、`m.` 子域）：按"指向哪个视频（及第几 P）"判重，而不是按字符串；早期按原样存下的旧剧集也要能认出来。`b23.tv` 短链离线无法展开，仍按原样比对。
- **分享文案里有多个链接**：取第一个可识别的视频链接。
- **剪贴板为空、是图片或是很长的文本**：视为"没有找到视频链接"，给出提示，不提交。
- **B 站合集 / 分 P 视频、YouTube 播放列表链接**：只提交链接所指的那一个视频（分 P 按链接里的页码）；纯播放列表页视为无法识别。
- **视频本身抓不到**（需要登录、地区限制、已删除）：失败通知带上系统给出的原因，记录可重试。
- **提交耗时较长**（系统要先把音频抓下来才确认）：用户在这期间不被阻塞，可以继续送下一个；"已收到"反馈必须先于最终结果到达。
- **隐私 / 无痕窗口**：与普通窗口同等对待。
- **系统通知被关闭**：功能照常，结果只出现在快捷提交记录里（User Story 2）。

## Requirements *(mandatory)*

### Functional Requirements

**接收**

- ~~**FR-001**~~ / ~~**FR-002**~~：链接协议与浏览器书签，已删除（2026-09-24）。
- **FR-003**: Podsum MUST 提供一个全局快捷键，默认 ⌥⌘S，用户可在设置中修改或关闭；快捷键在 Podsum 运行期间于任意 app 前台时生效。
- **FR-004**: 按下快捷键时，若最前面的 app 是 Safari、Google Chrome、Arc 或 Microsoft Edge，Podsum MUST 以其当前活动标签页的地址作为待提交链接，且不读剪贴板（见 User Story 1 场景 5）。
- **FR-005**: 按下快捷键时，若最前面的 app 不是上述浏览器，或读取标签页地址未获授权，Podsum MUST 从剪贴板文本中提取第一个可识别的视频链接（支持纯链接与分享文案）。
- **FR-006**: 首次读取某浏览器标签页时，Podsum MUST 触发系统授权请求；被拒绝时 MUST 按 FR-005 回退，并在反馈中说明如何补授权。

**识别与排队**

- **FR-007**: 只有 B 站与 YouTube 的单个视频链接（含 `b23.tv`、`youtu.be` 短链）被接受；其余链接 MUST 被拒绝并反馈"无法识别"，不得当作音频直链提交。
- **FR-008**: 所有入口 MUST 进入同一个快捷提交队列；队列 MUST 在 Podsum 退出后保留，重新启动后继续处理。
- **FR-009**: 队列中尚未完成的相同链接 MUST 只保留一份；重复送入时反馈"已在队列中"。
- **FR-010**: 队列 MUST 在后台依次提交，提交时使用默认的总结风格与详略（与提交面板不做任何选择时相同），不打开提交面板、不把 Podsum 窗口提到前台。
- **FR-011**: 后端未就绪（启动中、重启中、缺少配置）时，队列 MUST 暂停并保留链接，就绪后自动恢复。

**反馈**

- **FR-012**: 每次送入 MUST 在 2 秒内给出"已收到"反馈（系统通知），随后以最终结果更新同一条通知而非另起一条：已加入（带视频标题）/ 已经在库里 / 无法识别 / 失败（带原因）/ 等 Podsum 准备好（缺配置或后端未就绪）。
- **FR-013**: 点击"已加入"或"已经在库里"的通知 MUST 打开对应剧集详情。
- **FR-014**: Podsum MUST 保留最近的快捷提交记录（至少最近 50 条），显示链接或标题、来源入口、时间与结果；失败记录 MUST 可一键重试。
- **FR-015**: 系统通知权限被关闭时，FR-014 的记录 MUST 仍完整可用。

**生命周期**

- **FR-016**: 关闭 Podsum 主窗口后，Podsum MUST 继续在后台运行（后端不停），并在菜单栏常驻一个图标，使全局快捷键持续可用；菜单栏图标 MUST 提供"打开 Podsum"与"退出 Podsum"。只有显式退出（菜单栏"退出"或 ⌘Q）才停止 Podsum 及其后端。
- **FR-017**: 主窗口关闭后，点击程序坞图标、再次打开 Podsum、或点击快捷提交通知，MUST 重新打开主窗口。

### Key Entities *(include if feature involves data)*

- **快捷提交（Quick-Add Item）**：一次送入。属性：原始输入（链接或分享文案）、识别出的视频链接、来源入口（快捷键-浏览器 / 快捷键-剪贴板）、送入时间、状态（排队中 / 提交中 / 已加入 / 已存在 / 无法识别 / 失败）、失败原因、成功后关联的剧集。
- **快捷提交队列**：尚未到达终态的快捷提交的有序集合，跨启动保留；终态条目转为记录，按条数上限滚动淘汰。
- **剧集（Episode）**：沿用系统现有定义；一条成功的快捷提交对应一集。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 从"正在看视频"到"视频进入总结队列"，用户操作从 4 步（切到 Podsum、打开提交面板、粘贴、确认）降为 1 步（按快捷键；在浏览器以外的 app 里是"复制链接 + 按键"；首次使用的授权确认除外）。
- **SC-002**: 用户触发后 2 秒内看到"已收到"反馈，全程不离开当前视频页或 app。
- **SC-003**: 送入时后端尚未就绪（启动中、缺配置），链接在就绪后 100% 自动提交，无需用户进入 Podsum 做任何操作。
- **SC-004**: 在后端未就绪、Podsum 被退出再启动等情况下，已送入的链接零丢失、零重复提交。
- **SC-005**: 对一组覆盖 B 站长链 / 短链 / 分享文案、YouTube 长链 / 短链、非视频页的样例，识别结果（接受或拒绝）100% 符合预期。
- **SC-006**: 每一次送入都能在快捷提交记录里查到最终结果，没有"送出去了但不知道去哪了"的情况。

## Assumptions

- 本特性改变 002 客户端"关窗即退出"的约定（见 FR-016），002 README 中相关描述在实现时同步更新。
- 只做 Mac；手机端（iOS 快捷指令等）、系统分享菜单扩展、浏览器扩展均不在本轮，书签入口已删除。
- 后端提交接口、视频抓取、分享文案解析沿用现有能力。实现中发现两处必须改的后端行为（见 plan.md「后端改动」）：重复判定原本在下载**之后**、且按字符串精确比对——前者让"已经在库里"要等一整次下载，后者让地址栏写法与旧数据永远判不重。改为下载前判定、按视频身份比对，409 附带已有剧集 id。
- 后端确认一次视频提交需要先把音频抓下来，可能耗时数十秒——这正是 FR-012 要求"先回执、后结果"的原因。
- 快捷提交一律使用默认总结风格；需要定制风格时用户仍走现有提交面板。
- 受支持的浏览器限定为 Safari、Chrome、Arc、Edge（它们能被系统授权读取当前标签页）；Firefox 等只能走剪贴板（先复制链接再按键）。
- B 站 Mac 客户端没有可读取的地址栏，只能通过"复制链接 + 快捷键"覆盖。
- 单用户、本机使用，沿用 001 的"仅本机、无鉴权"前提。
